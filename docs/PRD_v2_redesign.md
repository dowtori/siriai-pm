## 1. 배경 및 문제 정의

### 1.1 실패의 진짜 원인

이전 두 차례 개편은 모두 **레이아웃 중심 설계**였다. 화면 구성을 먼저 정하고 기능을 거기 꿰맞췄다. 그러나 더 근본적인 문제가 있었다: **캠페인 진행 상태를 선형(1차원) 구조로 모델링한 것**.

현실의 캠페인 진행은 선형이 아니다.

```
❌ 현재 선형 모델 (틀림)
브랜드소통 → 모집중 → 컨펌단계 → 업로드 → 캠페인종료 → 입금확인
                                                         ↑
                                      이게 다 같은 "선" 위에 있어서 문제

✅ 실제 캠페인 구조 (입체형)
┌─ PHASE A: 납품 준비 ───┐   ┌─ PHASE B: 콘텐츠 ─┐   ┌─ PHASE C: 정산 ──┐
│  브랜드소통             │→  │  업로드 진행       │→  │  입금 대기       │
│  모집중                │   │  업로드 완료       │   │  입금 완료       │
│  컨펌 완료             │   └────────────────────┘   └──────────────────┘
└────────────────────────┘
```

이 때문에 발생하는 실제 혼란:
- "캠페인 종료" 상태인데 돈은 아직 안 받음 → 완료? 진행중?
- "완료" 탭 = 미입금 캠페인들이 섞여있음
- 업로드 84%인 캠페인과 모집중인 캠페인이 같은 "진행중"으로 분류됨
- "오늘 뭘 봐야 해?" 라는 가장 기본적인 질문에 답할 수 없음

### 1.2 이 PRD가 해결하는 것

1. **캠페인 라이프사이클을 3개의 독립 Phase로 재정의** → 입체적 상태 관리
2. **Phase 기반 다중 필터링** → 어떤 조합으로도 보기 가능
3. **레이아웃은 위 두 가지가 정의된 후 따라오는 것** → 이 순서가 중요

## 2. 캠페인 라이프사이클 재정의 (핵심)

### 2.1 3-Phase 모델

캠페인은 3개의 독립적인 Phase를 순차적으로 통과한다. 각 Phase가 모두 완료되어야 "전체 완료"다.

```
┌──────────────────────────────────────────────────────────────────────┐
│                     CAMPAIGN LIFECYCLE                               │
│                                                                      │
│  PHASE A         PHASE B              PHASE C                        │
│  납품 준비       콘텐츠 업로드         정산                            │
│  ─────────       ──────────────       ──────────                     │
│  ① 브랜드 소통   ④ 업로드 진행중      ⑥ 정산 대기                    │
│  ② 모집중        (N/M 진행률)         ⑦ 부분 입금                    │
│  ③ 컨펌 완료    ⑤ 업로드 완료 ✓     ⑧ 입금 완료 ✓                  │
│     (섭외 N명)                                                       │
│                                                                      │
│  [A완료: ①→③]   [B완료: 업로드율100%] [C완료: pay=입금완료]          │
│                                                                      │
│  전체 완료 = A완료 AND B완료 AND C완료                               │
│                                                                      │
│  ─────────────────────────────────────────────────────────────────  │
│  특수 상태 (어느 Phase와도 병렬 가능)                                  │
│  ↕ 상시 진행  — Phase A 없이 직접 업로드가 반복되는 캠페인             │
│  ⚠ 이슈       — 어느 단계에서든 이탈/문제 발생                        │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 Phase별 완료 조건 (DB 필드 매핑)

| Phase | 완료 조건 | 사용하는 필드 |
|-------|---------|-------------|
| **A. 납품 준비** | status가 ③ 이상으로 진행 | `status` ∈ {컨텐츠업로드, 캠페인종료, 입금확인} |
| **B. 콘텐츠** | 업로드율 100% OR 수동 완료 처리 | `count_upload >= count_select` AND `count_select > 0` |
| **C. 정산** | 입금 완료 | `pay_status = '입금완료'` |
| **전체 완료** | A AND B AND C | 모두 충족 |

> **DB 스키마 변경 없음**: 기존 `status`, `pay_status`, `count_upload`, `count_select` 필드만으로 3-Phase 판단 가능.

### 2.3 Phase 시각화 방식

목록에서 각 캠페인의 Phase 상태를 한눈에 보여준다.

```
캠페인명                      Phase 상태 표시
─────────────────────────────────────────────────────
무신사 봄 캠페인              [납품완료] [업로드 38/45] [미입금]
에스더버니 콜라보              [컨펌중  ] [업로드 전   ] [—     ]
올리브영 서머                  [납품완료] [업로드완료 ✓] [입금완료✓]  ← 전체완료
틈결 인비테이션                [컨펌중  ] [—           ] [—     ]
```

**Phase 배지 디자인:**

| 상태 | 색상 | 텍스트 |
|------|------|------|
| A: 브랜드소통 | 회색 | 브랜드소통 |
| A: 모집중 | 파랑 | 모집중 |
| A: 컨펌 완료 | 초록 (체크) | 납품완료 ✓ |
| B: 업로드 진행 | 노랑 | 38/45 (84%) |
| B: 업로드 완료 | 초록 (체크) | 업로드완료 ✓ |
| C: 정산 대기 | 회색 | 정산대기 |
| C: 미입금 | 빨강 | 미입금 |
| C: 부분 입금 | 주황 | 부분입금 |
| C: 입금 완료 | 초록 (체크) | 입금완료 ✓ |

### 2.4 "진행중" vs "완료" 재정의

기존: status = 캠페인종료/입금확인 이면 완료  
→ 오류: 미입금 캠페인이 완료로 분류됨

**신규 정의:**

```
진행중 = Phase A 또는 B 또는 C 중 하나라도 미완료
완료   = Phase A, B, C 모두 완료 (= 납품완료 AND 업로드완료 AND 입금완료)
보관   = is_archived = true (수동 아카이브)
```

> 이 정의로 인해 "캠페인 종료 + 미입금" 상태는 **진행중**으로 분류된다.  
> "돈 받을 때까지는 진짜 끝난 게 아니다"라는 업무 현실을 그대로 반영.

## 3. 다중 필터링 시스템

### 3.1 설계 원칙

- **모든 필터는 병렬 적용** (AND 조건): 거래처=무신사 AND Phase=정산 AND 미입금
- **필터 상태는 항상 화면에 보임** (칩 형태로)
- **필터 초기화 1클릭**
- **URL 상태 반영** (새로고침해도 필터 유지 — Phase 2)

### 3.2 필터 항목 정의

```
┌─ 필터 바 ─────────────────────────────────────────────────────────┐
│  [전체보기 ▾]  [Phase ▾]  [정산 ▾]  [거래처 ▾]  [+ 필터 추가]    │
│                                                                    │
│  현재 적용된 필터 칩:                                               │
│  [무신사 ×]  [미입금 ×]                                            │
│                                                    [필터 초기화]   │
└────────────────────────────────────────────────────────────────────┘
```

**필터 1: Phase 필터 (핵심)**

```
Phase 선택
──────────────────────────────
○ 전체
○ 납품 준비 중  (Phase A 미완료)
  └ 세부: [브랜드소통] [모집중] [컨펌중]
○ 업로드 진행 중 (Phase A완료, B미완료)
○ 정산 진행 중  (Phase B완료, C미완료)
○ 전체 완료     (A+B+C 모두 완료)
```

**필터 2: 정산 상태**

```
[전체] [미입금] [부분입금] [입금완료] [해당없음]
```

**필터 3: 거래처**

```
[전체] [무신사] [올리브영] [에스더버니] [틈결] ...
```

**추가 가능 필터:**

| 필터명 | 옵션 |
|-------|------|

| QA 상태 | 검수전 / 검수중 / 완료 / 이슈 |

## 4. 홈 뷰 재설계 (Phase 모델 반영)

기존 홈 = "D-day 기준 긴급도 정렬"  
→ 문제: D-day만 보면 정산 중인 캠페인이 올라와서 혼란

**즉시 확인 필요 섹션의 조건 정의:**

| 우선순위 | 조건 |
|---------|------|
| 🔴 최우선 | D-2 이내 AND Phase A 또는 B 미완료 |

## 5. 목록 뷰 상세 설계 (Phase 반영)

### 5.1 그룹핑

기본 그룹핑은 Phase 기준:

```
▼ 납품 준비 중 (7건)
  브랜드소통/모집중/컨펌 단계에 있는 캠페인들

▼ 업로드 진행 중 (4건)
  Phase A 완료, Phase B 진행중인 캠페인들

▼ 정산 진행 중 (3건)
  Phase B 완료, Phase C 미완료 (=미입금/부분입금)

▼ 전체 완료 (12건)                           [접힘 기본값]
  A+B+C 모두 완료

▼ 이슈/기타 (1건)
  status = 기타/이슈 또는 QA 이슈
```

### 5.2 목록 행 설계

```
☐  [A상태]     캠페인명                  거래처   [B: 업로드 현황]    [C: 입금]   D-day
─────────────────────────────────────────────────────────────────────────────────────
☐  [모집중 ▾]  무신사 봄 캠페인 2026     무신사   38/45 ████░ 84%   [미입금 ▾]  D-7
☐  [컨펌완료✓] 에스더버니 콜라보         에스더   45/45 ████▌100%  [미입금 ▾]  D+5
☐  [업로드▾]   틈결 인비테이션           틈결     12/20 ██░░░  60%  [—        ]  D-3
```

**컬럼 설명:**

| 컬럼 | 내용 | 편집 |
|-----|------|------|
| ☐ | 체크박스 | — |
| [A상태] | Phase A 현재 상태 배지 (클릭→변경) | 드롭다운 |
| 캠페인명 | 이름 (클릭→상세패널) | 상세패널에서 |
| 거래처 | 거래처명 | 인라인 |
| [B: 업로드 현황] | count_upload/count_select + 미니 진행바 | 숫자 인라인 |
| [C: 입금] | pay_status 배지 (클릭→변경) | 드롭다운 |
| D-day | 마감까지 일수 | 읽기전용 |

### 5.3 "A상태" 컬럼의 드롭다운

```
납품 준비 단계:
  ● 브랜드 소통
  ● 모집중
  ● 컨펌 완료
  ─────────────
  ● 업로드 진행중  ← Phase B 진입
  ─────────────
  ──────────────── (구분선, Phase 전환)
특수:
  ↕ 상시 진행
  ⚠ 이슈
```

Phase B는 A가 "컨펌 완료"된 이후 선택 가능하도록 권장 (강제 아님).  
Phase C(정산)는 B 완료 후 자동으로 pay_status 필드로 관리.

## 7. 상태 레이블 정리 (DB값 유지, UI 레이블만 변경)

DB에 저장되는 status 값은 **그대로 유지** (하위 호환성).  
UI에 표시되는 레이블만 Phase 맥락에 맞게 조정.

| DB 값 | Phase | UI 레이블 | 배지 색상 |
|------|-------|---------|---------|
| `1. 브랜드 소통` | A | 브랜드소통 | 회색 |
| `2. 모집중` | A | 모집중 | 파랑 |
| `3. 컨펌 단계` | A | 컨펌중 | 노랑 |
| `4. 컨텐츠 업로드` | B | 업로드중 | 초록 |
| `5. 캠페인 종료` | B→C 전환 | 납품완료 | 초록(체크) |
| `6. 입금 확인` | C | 입금확인중 | 보라 |
| `7. 상시 진행` | 특수 | 상시진행 | 청록 |
| `기타/이슈` | 특수 | 이슈 | 빨강 |

## 8. 핵심 계산 함수 (구현 스펙 확정)

### 8.1 Phase 상태 정의 (최종)

```
status 5 (캠페인 종료) = 납품 완료, 정산 시작 전
status 6 (입금 확인)  = 입금 진행 중 (Phase C)

→ status 5/6으로의 전환 = Phase B 수동 완료 처리
  (count_select 없어도, 드랍 처리해도, 강제 완료 가능)
```

### 8.2 완료 판단 함수

```js
// ── Phase A 완료: 컨펌이 끝나고 업로드 단계 이상으로 진입 ──
function phaseADone(c) {
  return ['4. 컨텐츠 업로드', '5. 캠페인 종료', '6. 입금 확인'].includes(c.status);
}

// ── Phase B 완료: OR 조건 ──────────────────────────────────
// 조건 1: status 5 또는 6 → 납품완료로 명시적 전환 (수동 force-complete)
// 조건 2: status 4 + count_select > 0 + count_upload >= count_select (자동)
// → "status를 5로 올리는 행위" 자체가 Phase B 강제 완료 처리
function phaseBDone(c) {
  if (['5. 캠페인 종료', '6. 입금 확인'].includes(c.status)) return true;
  if (c.status === '4. 컨텐츠 업로드' && c.count_select > 0) {
    return c.count_upload >= c.count_select;
  }
  return false;
}

// ── Phase C 완료: 입금완료 ────────────────────────────────
function phaseCDone(c) {
  return c.pay_status === '입금완료';
}

// ── 전체 완료 ─────────────────────────────────────────────
function isFullyDone(c) {
  return phaseADone(c) && phaseBDone(c) && phaseCDone(c);
}

// ── 그룹 분류 (목록 그룹 헤더 기준) ──────────────────────
function getPhaseGroup(c) {
  if (c.status === '7. 상시 진행') return 'ongoing';   // 상시 = 별도 그룹
  if (c.status === '기타/이슈' || c.qa_status === '이슈') return 'issue';
  if (isFullyDone(c)) return 'done';
  if (phaseBDone(c))  return 'settlement';  // B완료, C미완료 = 정산 대기
  if (phaseADone(c))  return 'upload';      // A완료, B미완료 = 업로드 진행중
  return 'delivery';                         // A미완료 = 납품 준비
}

// ── 긴급 여부 ─────────────────────────────────────────────
function isUrgent(c) {
  if (isFullyDone(c) || c.is_archived) return false;
  const nearDeadline = c._dday !== null && c._dday >= 0 && c._dday <= 2;
  const hasIssue     = c.status === '기타/이슈' || c.qa_status === '이슈';
  const unpaidDone   = phaseBDone(c) && !phaseCDone(c); // 납품완료인데 미입금
  return nearDeadline || hasIssue || unpaidDone;
}
```

### 8.3 Phase B 업로드 현황 표시 규칙

| 상황 | 표시 |
|------|------|
| status=4, count_select > 0 | `38/45` + 진행바 (84%) |
| status=4, count_select = 0 | `업로드중` (숫자 없음) |
| status=5 또는 6 | `납품완료 ✓` (초록) |
| status=1,2,3 | `—` (아직 업로드 단계 아님) |

### 8.4 필터 함수

```js
function applyFilters(campaigns, filters) {
  let data = campaigns.filter(c => !c.is_archived);

  // Phase 그룹 필터
  if (filters.phase && filters.phase !== 'all') {
    data = data.filter(c => getPhaseGroup(c) === filters.phase);
  }

  // 정산 상태 필터
  if (filters.payStatus) {
    data = data.filter(c => c.pay_status === filters.payStatus);
  }

  // 거래처 필터
  if (filters.client) {
    data = data.filter(c => c.client_name === filters.client);
  }

  // 검색
  if (filters.search) {
    const q = filters.search.toLowerCase();
    data = data.filter(c =>
      (c.name || '').toLowerCase().includes(q) ||
      (c.client_name || '').toLowerCase().includes(q) ||
      (c.detail || '').toLowerCase().includes(q)
    );
  }

  return data;
}
```

## 12. 핵심 아키텍처 결정 사항

### Phase B 완료 조건 (OR)
두 가지 경로 중 하나면 Phase B 완료:
1. **자동**: `status = '4. 컨텐츠 업로드'` + `count_upload >= count_select > 0`
2. **수동**: `status`를 5 또는 6으로 올리는 행위 자체 = force-complete

이 설계로 ① 수량 미설정, ② 드랍 인플루언서 제외 완료, ③ 강제 마감 처리 케이스 모두 커버.

### DB 스키마 무변경
기존 `status`, `pay_status`, `count_upload`, `count_select` 4개 필드만으로 3-Phase 판단 가능. 마이그레이션 없음.

### 상세 패널 동작 방식
- `width: 0 → 480px` push 방식 (메인 영역이 실제로 좁아짐)
- 동일 캠페인 재클릭 시 토글(닫힘)
- 캠페인 전환 시 내용만 교체 (패널 재슬라이드 없음)

### 렌더링 전략
- `App.renderAll()` — 전체 재렌더 (Supabase 실시간 업데이트 시)
- `App.setFilter()` — 헤더 + 목록만 재렌더 (필터 변경 시)
- `App.selectCampaign()` — 행 선택 상태 + 상세 패널만 업데이트 (캠페인 클릭 시)
- `App._rerenderRow()` — 단일 행만 교체 (인라인 편집 후)
